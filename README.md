# The Service and UMC — CRM автосервиса

Внутренняя CRM для автосервиса: запись и подъёмники, заказ-наряды, склад, закупки, услуги, клиенты, сотрудники, финансы, кассовые смены и документы.

## Что уже работает

- заказ-наряды со статусами, работами, запчастями, оплатами и отдельной клиентской печатной версией;
- частичная и смешанная оплата: наличные / терминал / перевод;
- возвраты клиенту и поставщику;
- кассовая смена с начальным остатком, пересчётом и расхождением;
- склад с резервом под заказ, историей движений и закупками;
- дробные складские количества для масел, жидкостей и расходников;
- хранение как по ячейкам, так и без ячейки («быстрый доступ»);
- мини-справочник артикулов: OE-номера, кросс-номера и применяемость;
- внутренние расходники заказа (смазки, очистители, аэрозоли), которые распределяются внутри стоимости работ и не выводятся клиенту отдельной строкой;
- расчёт зарплаты, финансы, отчёты и резервные копии;
- Supabase: авторизация, общая база, роли, синхронизация, офлайн-retry, история и серверные резервные копии;
- сервисная книжка по каждому автомобилю;
- готовые WhatsApp/SMS-сообщения о готовности автомобиля;
- PWA-установка на телефон/ПК и базовый офлайн-кэш интерфейса;
- чек-лист готовности к переходу с демо-данных на реальные.
- два телефона компании и логотип в печатных документах;
- быстрые фильтры прайс-листа по категориям;
- более плотные мобильные списки без лишних вложенных полей;
- роль механика с экраном «Мои работы сегодня» и кнопками Старт / Пауза / Готово;
- роль бухгалтера с доступом только к финансам, отчётам, сотрудникам и документам;
- фото/видео приёмки, диагностики, ремонта и результата в истории заказ-наряда;
- фото перед загрузкой автоматически уменьшаются до 800 px по ширине и сохраняются в WebP quality 0.7 (JPEG fallback), как в MyappforBT;
- сканирование штрихкодов камерой телефона при поиске и приёмке запчастей.

Полное описание требований: [docs/requirements.md](docs/requirements.md).

## Стек

React + Vite + TypeScript + Tailwind CSS v4.

CRM умеет работать:
- локально через `localStorage`, если Supabase не подключён;
- с общей серверной базой Supabase — для нескольких сотрудников и устройств.

Подключение сервера: [docs/SUPABASE_SETUP.md](docs/SUPABASE_SETUP.md).

## Справочник запчастей и VIN

В CRM заложена собственная лёгкая база:
- основной артикул;
- OE-номера;
- кросс-номера / заменённые номера;
- краткая применяемость;
- ссылка на внешний каталог;
- поиск по артикулу, аналогу и автомобилю.

Это не должно заменять профессиональный каталог. Финальная применяемость запчасти всегда проверяется по VIN.

### Куда развивать интеграцию

Наиболее подходящее направление — **TecDoc / TecAlliance**:
- поиск по VIN;
- поиск по OE и артикулу;
- привязки «автомобиль → группа деталей → конкретные артикулы»;
- Web Service API для интеграции прямо в CRM.

Также можно использовать **partslink24** как внешний OEM-каталог: открыть каталог по VIN и перейти к оригинальным схемам/деталям.

Архитектурный план интеграции:
1. В карточке автомобиля кнопка «Подобрать запчасти по VIN».
2. VIN передаётся в внешний каталог/API.
3. Пользователь выбирает узел и деталь.
4. В CRM возвращаются артикул, OE-номер, название, бренд и применяемость.
5. CRM ищет совпадение на своём складе и показывает остаток/ячейку/цену.
6. Если позиции нет — «Добавить в закупки» или «Завести на склад».

Пока API не подключён, вкладка **Склад → Справочник артикулов** работает как собственный мини-каталог.

## Правило применения данных после опроса сервера

CRM применяет любой ответ сервера по одному правилу:

1. **Ревизия никогда не уменьшается.** Ответ с ревизией ниже уже применённой игнорируется.
2. **Старый параллельный опрос не меняет экран после нового.** Его ошибка также не переводит CRM в ошибочное состояние.
3. **Свежий серверный снимок не затирает неподтверждённые локальные изменения целиком.** Используется трёхстороннее слияние: последняя общая версия → локальная версия → свежая серверная версия.
4. **Разные сущности и разные поля одной сущности объединяются.** Например, локальная смена статуса заказа и серверная заметка сохраняются одновременно.
5. **Если одно и то же поле изменено на двух устройствах по-разному, серверное подтверждённое значение имеет приоритет.** Остальные локальные изменения сохраняются, конфликт учитывается в Настройках.
6. **Удаление не выполняется вслепую.** Если локально объект удалён, а на сервере после этого изменён, серверная версия сохраняется. Подтверждённое серверное удаление не воскрешается старой локальной правкой.
7. **Все критичные RPC** — создание заказа, оплаты, касса, склад, автомобили — проходят через тот же шлюз ревизий и слияния.

## Правило синхронизации с сервером

1. Каждое состояние сервера имеет монотонную `revision`; устройство никогда не применяет ревизию меньше уже подтверждённой.
2. Запоздавший ответ старого опроса и ошибка старого запроса не меняют текущий интерфейс.
3. Последняя подтверждённая серверная версия хранится как `base`. Если после неё есть локальные изменения, свежий ответ сервера не заменяет локальную базу целиком.
4. Используется трёхстороннее слияние `base → local → remote`: изменения разных записей и разных полей одной записи объединяются.
5. Если одно и то же поле одновременно изменено по-разному, приоритет у уже зафиксированного серверного значения; конфликт считается и показывается в Настройках.
6. Удаление не «воскрешает» и не стирает сущность молча: конфликт удаления с параллельным изменением фиксируется отдельно.
7. Все мутации с одного устройства выполняются последовательно. Между разными устройствами критичные операции дополнительно защищены серверными атомарными RPC.
8. Создание заказов, оплаты, касса, резерв/приёмка/возврат склада и управление автомобилями подтверждаются сервером до того, как считаются завершёнными.

## Защита данных и одновременная работа

- серверная база имеет ревизии;
- конфликтующие изменения сливаются, а не молча затираются;
- при обрыве сети изменения остаются на устройстве и отправляются повторно;
- чужие изменения подтягиваются автоматически;
- при выдаче CRM повторно проверяет фактический остаток и не даёт списать больше, чем реально есть;
- резерв учитывается по всем открытым заказам;
- резерв запчасти подтверждается атомарно на сервере: два сотрудника не могут одновременно забрать одну и ту же последнюю единицу;
- приёмка и возврат поставщику также атомарны: параллельные операции не перетирают остаток и не занимают одну ячейку двумя позициями;
- при конфликте остатка CRM получает свежую серверную базу и показывает актуальное количество;
- оплаты и возвраты клиентов подтверждаются атомарно на сервере: два устройства не могут одновременно закрыть один и тот же остаток долга;
- открытие и закрытие кассовой смены подтверждается сервером, поэтому одновременно может существовать только одна открытая смена;
- создание клиента, автомобиля и заказ-наряда выполняется атомарно: номера не дублируются, а сервер повторно проверяет телефон, госномер/VIN и занятость подъёмника;
- отдельное добавление, редактирование и удаление автомобиля из карточки клиента тоже подтверждается сервером: одинаковый госномер/VIN не сохранится, а автомобиль с историей заказов удалить нельзя;
- ручные расходы, выплаты зарплаты и подтверждение возврата от поставщика идемпотентны: повтор запроса с тем же operation id не создаёт второе движение денег;
- смена статуса и выдача автомобиля выполняются атомарно: повтор после таймаута не списывает/возвращает запчасти второй раз, а сервер заново проверяет работы, переплату и фактический остаток;
- редактирование клиента и прайс-листа подтверждается сервером: повтор того же сохранения — no-op, дубли телефона и одинаковых услуг блокируются, повторное удаление услуги безопасно;
- снятие резерва и удаление незакрытого заказа идемпотентны: движение «Снят резерв» имеет детерминированный ID, повтор не создаёт дубль, а сервер заново проверяет статус и оплаты перед удалением;
- при выходе локальная рабочая база очищается с устройства.

## Состояние проекта после ревью и оптимизации

На текущем этапе выполнено техническое ревью CRM, исправлены гонки синхронизации, усилена серверная безопасность и оптимизирована загрузка интерфейса.

### Что уже исправлено и оптимизировано

- CSP в production вставляется первой в `<head>` и применяется до загрузки Vite-бандла.
- Сетевой CSP ограничен текущим Supabase origin вместо общего разрешения на любой `https:` адрес.
- Устранены stale snapshot / multi-device гонки при редактировании клиентов, автомобилей и услуг.
- `dbRef.current` синхронизируется во всех прямых заменах состояния, включая загрузку сервера, merge, сброс и импорт.
- При одновременной работе устройств локальная дельта накладывается на свежую серверную запись, а не на устаревший снимок.
- JSON-восстановление запрещено поверх уже работающей общей базы; для рабочей Supabase-базы используются серверные резервные копии.
- Перед серверным восстановлением автоматически создаётся копия `before_restore`.
- Фото/видео заказа считаются сохранёнными только после подтверждения метаданных сервером.
- При неудачном сохранении метаданных загруженный Storage-файл удаляется best-effort cleanup.
- При удалении медиа сначала подтверждается изменение заказ-наряда, затем удаляется сам Storage-объект.
- Фото автоматически сжимаются до 800 px по ширине, WebP quality 0.7, JPEG fallback.
- Главные страницы переведены на lazy loading/code splitting.
- Основной JS-бандл уменьшен примерно с 759 КБ до 237 КБ (gzip примерно с 200 КБ до 74 КБ).
- Refresh-token больше не хранится постоянно в `localStorage`; используется `sessionStorage`, старая запись удаляется при миграции.
- GitHub Actions переведены на least privilege: права выдаются отдельно нужным jobs.
- Официальные GitHub Actions закреплены на конкретные commit SHA вместо плавающих `@v3/@v4`.
- Service Worker кэширует только статические ресурсы CRM и навигационный shell, а не произвольные same-origin GET-запросы.
- Pages deploy не блокируется временной high-уязвимостью транзитивной dev-зависимости, но обычный CI по-прежнему проверяет `npm audit --audit-level=high`.
- Серверные RPC для заказов, склада, оплат, кассы, автомобилей, клиентов и услуг защищены атомарностью/идемпотентностью там, где это критично.
- Миграция `019_review_fixes.sql` исправляет расчёт кассы и корректное очищение optional-полей.
- Миграция `020_security_hardening.sql` усиливает Storage и запрещает ограниченным ролям обходить атомарные финансовые RPC через общий `crm_save_state`.
- Storage в схеме 020 проверяет workshop, существование заказ-наряда, роль, структуру пути, расширение и разрешённый MIME.
- Настройки CRM требуют серверную схему не ниже **20**.
- Добавлены regression/security tests для CSP, deploy workflow, JSON restore, media sync, code splitting, токенов, Storage и server role restrictions.
- Последний проверенный CI: **127/127 тестов**, **0 vulnerabilities**, lint без ошибок, production build проходит.

## Дополнительное ревью после security-набора

После внедрения migration 020 проведено повторное ревью поведения приложения и найденные замечания закрыты:

- lazy-loaded маршруты защищены `AppErrorBoundary`; ошибка загрузки чанка больше не должна приводить к белому экрану;
- событие Vite `vite:preloadError` перезагружает приложение после редеплоя со старыми именами чанков;
- операции добавления/удаления медиа больше не подменяют всю базу `cloudBaseRef`-снимком: media-дельта перебазируется на свежий `dbRef.current`;
- если первый media push не подтверждён актуальной server-base, выполняется дополнительное подтверждение перед сообщением об успехе;
- удаление заказ-наряда запускает best-effort удаление его Storage-файлов;
- migration 020 позволяет owner/partner/advisor увидеть и удалить orphan-файлы уже удалённого заказа, но запрещает загрузку новых файлов в несуществующий заказ;
- production build теперь останавливается, если `VITE_SUPABASE_URL` отсутствует/не HTTPS или отсутствует `VITE_SUPABASE_ANON_KEY`;
- импорт JSON в состоянии `needs_upload` сохраняется локально до успешного первичного переноса в Supabase и не теряется при перезагрузке вкладки;
- AuthProvider не падает, если Web Storage заблокирован браузером;
- при откате медиа ошибка серверного сохранения показывается пользователю первой, а не скрывается за ошибкой отдельного файла.

### Решение по хранению сессии

Refresh-token остаётся в `sessionStorage` намеренно.

Это **не является основной защитой от XSS** — основную защиту дают CSP и отсутствие опасного HTML. Причина выбора `sessionStorage` другая: на общем цеховом планшете вход не должен оставаться сохранённым навсегда после закрытия приложения/браузера.

Компромисс:
- после полного закрытия PWA/браузера сотруднику может потребоваться войти снова;
- новая вкладка не обязана наследовать уже открытую сессию;
- зато refresh-token не остаётся долговременно в профиле устройства.

Если позже для постоянного цехового планшета потребуется режим «доверенное устройство», его нужно делать отдельной функцией с явным выбором пользователя, а не возвращать постоянное хранение токена по умолчанию.

1. Сделать отдельную резервную копию текущей рабочей базы.
2. В Supabase выполнить все миграции **001 → 020 строго по порядку**.
3. Особо проверить, что применены:
   - `019_review_fixes.sql`;
   - `020_security_hardening.sql`.
4. Открыть **Настройки → Готовность к реальной работе** и убедиться, что сервер показывает **схему 20 · актуально**.
5. Проверить пользователей Supabase Authentication и роли:
   - owner;
   - partner;
   - advisor;
   - parts;
   - mechanic;
   - accountant.
6. Убедиться, что каждому пользователю назначен правильный workshop и активное членство.
7. Проверить, что bucket `order-media`:
   - private;
   - лимит файла 25 МБ;
   - содержит только разрешённые MIME;
   - работает через актуальные Storage policies.
8. Проверить production variables GitHub/Supabase:
   - `VITE_SUPABASE_URL`;
   - `VITE_SUPABASE_ANON_KEY`.
   В клиент никогда не добавлять `service_role`, пароль БД или другие серверные секреты.
9. Заменить демонстрационные данные реальными:
   - компания;
   - телефоны;
   - ИНН/ответственный;
   - сотрудники;
   - механики;
   - прайс;
   - склад;
   - рабочие часы.
10. Сделать ручную серверную резервную копию непосредственно перед первым рабочим днём.
11. Проверить печатный заказ-наряд на реальном принтере A4.
12. Проверить CRM минимум на одном компьютере и одном телефоне.
13. Выполнить локально/в CI:
    ```bash
    npm ci
    npm audit --audit-level=high
    npm test
    npm run lint
    npm run build
    ```
14. Не начинать реальную эксплуатацию, если CI красный или Настройки показывают серверную схему ниже 20.

## Контрольный прогон перед первым рабочим днём

Обязательно проверить реальную одновременную работу нескольких ролей.

- Владелец на устройстве A редактирует клиента, приёмщик на устройстве B меняет другое поле этого клиента — оба изменения должны сохраниться.
- Два устройства пытаются зарезервировать последнюю единицу одной запчасти — второй запрос должен получить актуальный конфликт остатка.
- Два устройства пытаются принять оплату одного остатка долга — двойная оплата не должна появиться.
- Одновременно открыть кассовую смену с двух устройств — открытой должна остаться только одна.
- Приёмщик создаёт заказ, механик видит только назначенные ему работы.
- Механик добавляет фото к своему заказу и не получает доступ к чужому.
- Запчастист не может удалять медиа.
- Бухгалтер не должен иметь возможность менять склад/заказы через UI и прямой общий sync RPC.
- Отключить интернет во время обычной некритичной правки, затем вернуть связь и проверить синхронизацию.
- Проверить серверную резервную копию и тестовое восстановление на безопасной копии данных.
- Проверить выход из аккаунта: локальная рабочая база и merge-cache должны очищаться с устройства.

## Что проверить СРАЗУ ПОСЛЕ публикации

1. Открыть опубликованную CRM в новом/private окне, чтобы исключить старый кэш.
2. Проверить вход каждого типа пользователя.
3. Проверить, что в **Настройки** отображается серверная миграция 20.
4. Создать тестового клиента, автомобиль и заказ-наряд.
5. Добавить работу и запчасть.
6. Добавить фото, открыть его повторно, затем удалить.
7. Провести тестовую оплату и возврат только на тестовых данных.
8. Открыть/закрыть тестовую кассовую смену.
9. Создать серверную резервную копию и убедиться, что она появилась в истории.
10. Проверить журнал действий.
11. Проверить печать заказ-наряда на ПК и телефоне.
12. Проверить PWA после обновления: если устройство держит старый shell, полностью закрыть приложение и открыть заново.
13. Убедиться, что GitHub Pages deployment завершился успешно и Pages-ветка совпадает с `main`.
14. После первых реальных операций ещё раз сделать серверный backup.

## Что контролировать после запуска

- раз в день смотреть статус синхронизации и ошибки в Настройках;
- регулярно проверять наличие автоматических/ручных серверных backup;
- не применять новые SQL-миграции без резервной копии;
- перед обновлением production сначала дождаться зелёного CI;
- не редактировать критичные массивы Supabase вручную через Dashboard;
- денежные и складские операции проводить только через интерфейс CRM/предусмотренные RPC;
- при конфликте нескольких устройств сначала обновить состояние с сервера, а не повторять операцию много раз;
- периодически выполнять `npm audit` и обновлять зависимости;
- после изменения ролей обязательно повторять role/access smoke-test;
- следить за объёмом Storage и при необходимости чистить подтверждённые orphan-файлы;
- при существенных изменениях повторять многопользовательский тест на двух устройствах.

## Вопросы Игорю перед следующим этапом

Перед разработкой следующих функций нужно сначала уточнить реальные процессы сервиса.

1. **Расширенный справочник артикулов**
   - нужен ли отдельный пункт меню «Справочник артикулов»;
   - нужен ли справочник примерно на **1000+ позиций**;
   - какие бренды и группы деталей приоритетны;
   - нужны ли для каждой позиции: оригинальный OE-номер, заменители/аналоги, применяемость, бренд, комментарий и источник данных;
   - использовать только данные из проверенных источников и не добавлять сомнительные кроссы автоматически.

2. **Отзывы и репутация**
   - нужно ли подтягивать отзывы из Яндекс Карт / Яндекс Бизнеса;
   - нужна ли статистика по рейтингу, количеству отзывов, положительным/негативным отзывам и динамике;
   - нужно ли создавать задачу/уведомление при новом плохом отзыве;
   - нужно ли после завершённого заказа напоминать клиенту оставить отзыв;
   - через какой канал просить отзыв: WhatsApp, SMS, QR-код в заказ-наряде, ссылка после оплаты.

3. **Оплата**
   - нужна ли онлайн-оплата из CRM;
   - нужен ли СБП/QR;
   - нужно ли связывать CRM с банковским терминалом;
   - нужно ли автоматически отмечать заказ как оплаченный после подтверждения платёжного провайдера;
   - какой банк/эквайринг/терминал уже используется в сервисе.

4. **Другие интеграции**
   - телефония и запись звонков;
   - WhatsApp/SMS-уведомления;
   - онлайн-касса/чеки;
   - поставщики и каталоги запчастей;
   - VIN/каталоги применяемости;
   - бухгалтерия;
   - календарь/запись;
   - резервные копии/экспорт данных.

Эти пункты **не реализовывать заранее**: сначала получить ответы Игоря и только после этого выбирать конкретные API и архитектуру.

## Что ещё осталось перед боевым запуском

Проверьте **Настройки → Готовность к реальной работе**. CRM отдельно подсвечивает:
- телефон сервиса;
- полноту прайс-листа;
- реальные имена механиков;
- замену демонстрационных клиентов/машин/заказов;
- состояние общей базы;
- наличие резервной копии;
- актуальность серверных миграций Supabase, минимум **20**.

Автоматический расчёт сдельной зарплаты уже реализован: начисление идёт по выданным заказам и работам конкретного исполнителя.
